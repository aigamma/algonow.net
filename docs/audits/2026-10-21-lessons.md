# Audit of the engineering lessons, 2026-10-21 (with the 2026-10-22 follow-up)

Scope: all 29 published lessons. Mechanical layer: the full engineering
checker with every Python suite (29 packages), `npm test` (306 tests at the
time), live probes of all 29 pages (home card, page chunk, manifest chunk,
both audio objects 200). Reading layer: each lesson's `solution.py`, expected
outputs, page brief, walkthrough, evidence, tradeoffs, practice text, and the
recorded narration where a claim was in doubt; one unpinned numeric claim
(class balancing, seed 12) recomputed and confirmed.

Auditor: Claude Fable 5 (the authoring model), reading its own work against
the code and the fixtures. The open items below are for a second engine.

## How a second engine should use this

Per the operating contract (CLAUDE.md, rule 10), other engines audit; they do
not author. Read each item, check the claim against the cited file and line,
and report a verdict with its reasoning. Any text change is then made by
Fable in the registry, the page, and the narration together, and the page is
re-recorded when the spoken prose changes (a narration edit invalidates the
published tracks; `npm run check` enforces that).

To rerun the mechanical layer:

```
npm run check                 # structure, registry, narration bindings, tests
npm run check:engineering     # every lesson's Python suite and both primary files alone
npm run build && npm run qa   # link crawl, prose scan, desktop and phone browser sweeps
```

## For a second engine to review (judgment calls, left as written)

Each item names the exact text and where it lives. The question is whether
the wording would mislead an expert reader, not whether the code is right
(the code is checked by the suites).

1. **"most hosted embedding models return unit-length vectors"** (a market
   claim, not a code fact). True of several major providers; whether "most"
   holds across today's hosted models is the question.
   - `scenarios/cosine-top-k-retrieval/content.jsx:219-220` (the limits
     paragraph: "most embedding models already return unit-length vectors")
   - `scenarios/cosine-top-k-retrieval/content.jsx:248` (tradeoff 1,
     preferWhen: "which most hosted embedding models do")
   - `src/content/cosine-top-k-retrieval.narration.js:35` (the spoken form of
     tradeoff 1; a change here means re-recording the page)
   - Possible softening if the reviewer objects: "many hosted embedding
     models" or "the major hosted embedding models document unit-length
     output". Either keeps the code and the numbers unchanged.

2. **"the standard library's shuffle is the same on every machine for the
   same seed."** True across platforms, and stable across CPython versions in
   practice since 3.2; not a formal language guarantee. The documentation
   guarantees only that `random()` keeps its sequence for a given seed, while
   "most of the random module's algorithms and seeding functions are subject
   to change across Python versions". `shuffle` uses `_randbelow`, which has
   not changed since 3.2.
   - `scenarios/batch-examples-with-seeded-shuffle/content.jsx:118`
   - `src/content/batch-examples-with-seeded-shuffle.narration.js:30` (the
     same sentence, spoken; a change means re-recording)
   - Possible refinement: "the same on every machine running the same Python
     version for the same seed" (and the same `random.Random` class, which
     the file already pins).

3. **Percentile naming.** The helper rounds the position `share x (n - 1)`
   and the page calls it "nearest rank, one of several conventions". A
   statistician may prefer "nearest position with rounding" or note that the
   textbook nearest-rank method uses ceiling of `share x n` (positions 5 and
   195 on 200 values, against 5 and 194 here).
   - `scenarios/benchmark-bootstrap-interval/python/src/bootstrap_eval/solution.py:29-34`
   - `scenarios/benchmark-bootstrap-interval/content.jsx:33`, `:171-174`
     (the walkthrough, which shows the arithmetic), `:220-221` (the limits
     paragraph)
   - The interval endpoints on the page follow from the code as written and
     would move by one position under the ceiling variant; the lesson's
     verdict (the interval includes zero) does not change.

4. **pass at k, two forms of one identity.** The registry summary names the
   estimator as "one minus C(n minus c, k) over C(n, k)"; the code and the
   page use the equal counted form "(C(n, k) minus C(n minus c, k)) over
   C(n, k)" and explain why (the counted form reads as "subsets with a pass
   over all subsets"). Both are the Codex-paper estimator.
   - `src/data/engineering.js:350` (the summary, visible on the Home card and
     the page lead)
   - `scenarios/pass-at-k-estimator/content.jsx:30-32`, `:159`
   - `scenarios/pass-at-k-estimator/python/src/pass_at_k/solution.py:38`
   - Question for the reviewer: should the summary use the counted form so
     the three places read identically?

5. **Grounding figure, score labels near the crossing links.** Closed on
   2026-10-22. The scores for sentences 2 and 3 ("0.857" and "0.167") sit
   where the c1 to sentence-3 link crosses the c2 to sentence-2 link. On a
   390 px phone viewport the figure is a thumbnail until "Enlarge diagram";
   enlarged, it draws the same geometry on a 1350 by 729 canvas inside a
   sideways-scrolling box, where the two labels are 38 px apart with no
   overlap and fully legible (capture taken at step 6 of 8 through
   `scripts/qa/cdp.mjs`, the enlarged canvas read from its own pixels). The
   canvas text audit reports no overlap at any step. No change.
   - `scenarios/grounding-check-by-sentence-overlap/visuals/GroundingViz.jsx`

## Near-duplicate review

No two lessons teach the same action; none recommended for deletion. The
closest pairs, all distinct in purpose and in the Python they teach:

- exact-match-and-token-f1 and grounding-check-by-sentence-overlap: both
  normalize words into sets and measure overlap, one to score an answer
  (Counter, precision, recall, F1), one to check faithfulness (set
  intersection over the sentence, best chunk, threshold).
- stable-split-by-hash and incremental-ingest-by-content-hash: both use
  hashlib SHA-256, one to assign a split from an id, one to detect content
  changes against a manifest.
- distill-soft-targets, kl-divergence-per-example, and
  truncate-teacher-top-k: all distillation; targets and loss, a per-example
  diagnostic, and storage of sparse targets.
- paired-prompt-comparison and benchmark-bootstrap-interval: both compare two
  models on paired items; a two-by-two count with named regressions against
  a resampled interval.
- batch-examples-with-seeded-shuffle and balance-classes-by-downsampling:
  both use random.Random(seed) and group by label; batching an epoch against
  capping a class.
